# CM-J05: Integrated journey litmus and delivery

Revision: 1. Status: ready for implementation and verification. Date: 2026-11-13.
Basis and method identities: [CM-J01](CM-J01.md). Depends on CM-J01 through CM-J04.

## Observable end state

An individual builder on the qualified Windows AMD64 route installs the reviewed preview, approves exact sources and destinations, obtains actual usage with understandable coverage, explicitly reports progress, regenerates the snapshot, records a human-chosen decision and retrieves it. Saved evidence and private state survive update, rollback, interruptions and repeated actions. Automated delivery and actual Jo acceptance/usefulness are distinct.

## Verification and delivery requirements

1. Reconcile actual source, installed version, current worktrees and publication owners. Use isolated candidates and one publishing owner per repo. Preserve legacy stable, Directory branch/submission, old OA/Todoist trial, Espansr changes and unrelated article/site work.
2. Run relevant tests and all permitted normal checks. Verify real rendered layout/keyboard/responsive/focus/contrast where allowed; document specific access limitations. Review changes against the specs and the template baseline. Never count an excluded/denied test as passed or retry it by another route.
3. Build a new numbered preview from canonical committed bytes. Verify package/source provenance, manifest file hashes, release checksums, signed-out links and downloaded bytes. Keep qualification claims scoped to evidence, including Windows existing-device versus clean consumer/non-admin and Mac/ARM boundaries.
4. Exercise fresh isolated profile installation, declared-server discovery, update and rollback with retained synthetic state. Install the checked candidate through supported controls on the permitted JO path while preserving existing interpreter settings, config, history, reports and independent helper. Do not enable duplicate plugins or silently expand telemetry/permissions.
5. Use a bounded live canary only within existing actual source authority. Compare installed/source identities, run an actual-source report, and preserve partial/unassigned coverage. A synthetic demo cannot satisfy real usage; direct stdio cannot establish an authenticated model-driven client journey.
6. Exercise report -> explicit checkpoint -> regeneration -> explicit decision -> retrieval with known synthetic assertions. Separately request the human's real checkpoint/decision/value judgment when absent; never write a fabricated human judgment into production state.
7. Update actual install/use/recovery docs and Cherry Bridge Resources/product copy to verified behavior and exact release links. Preserve the existing product URL and Resources card. Use existing GitHub/Cloudflare delivery and verify deployed revision and live page. No external outreach, paid services, new subscriptions, SSO enablement, Directory resubmission or auto-publish changes.
8. Report exact spec revisions, check results and exclusions, release/tag/checksums, installed readback, site revision/URL, litmus observations and remaining human/access actions. Ready specs or passing builds do not equal human acceptance or complete usefulness evidence.

## Journey expectations before observation

| Step | Expected evidence | Starting status |
| --- | --- | --- |
| Discover/install | Correct preview route; exact installed version, source and interpreter | Unverified for new candidate |
| Approve/report | Exact plan and real usage with visible gaps | Existing 1.2.0 historical only |
| Understand coverage | Person distinguishes unknown, zero, unassigned and partial | Human judgment unverified |
| Report progress | Only an explicit checkpoint changes operator history | Source owner exists |
| Refresh | New timestamp/identity; old report unchanged | Source owner exists; MCP guidance missing |
| Decide/retrieve | Exact snapshot-bound immutable decision and preserved later history | Adapter required by CM-J04 |
| Value | Jo explains a useful decision from the report | Human action required |

No unresolved product decision blocks implementation. Inaccessible tests, unsupported platforms, sign-in requirements and missing human facts remain precise verification boundaries rather than invented passes.
